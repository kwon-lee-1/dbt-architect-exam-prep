### Q1. ⭐
> **Subdomain 10.1 — `@` graph operator vs `+model+`**

A data engineer wants to run `model_x` and all of its descendants, but also wants to ensure that every ancestor of every descendant is included so that the full graph is self-consistent. Which selector achieves this?

- A) `+model_x+`
- B) `model_x+`
- C) `@model_x`
- D) `model_x*`

> [!success]- Answer & Explanations
> **✅ Correct: C**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `+model_x+` = all ancestors of `model_x` **plus** all descendants of `model_x`. It does NOT include ancestors of the descendants — only ancestors of `model_x` itself. |
> | **B) ❌ Incorrect** | `model_x+` = `model_x` and all its descendants, but none of their ancestors. |
> | **C) ✅ Correct** | `@model_x` is the **full closure operator**. It expands to: `model_x` + all descendants of `model_x` + all ancestors of every one of those descendants. Use it when you need a complete, self-contained subgraph — everything needed to rebuild `model_x` and validate all downstream consumers. |
> | **D) ❌ Incorrect** | `model_x*` is not valid dbt selector syntax. |
>
> > 💡 **Key rule**: `@model` = model + descendants + **all ancestors of descendants**. `+model+` = model's own ancestors + model + model's own descendants. The `@` operator is uniquely needed for full-closure subgraph runs.

### Q2. ⭐
> **Subdomain 10.2 — Set operator: union vs intersection**

A CI job needs to run only models that are both modified AND tagged `nightly`. Which dbt selector syntax correctly expresses this intersection?

- A) `state:modified tag:nightly`
- B) `state:modified,tag:nightly`
- C) `state:modified+tag:nightly`
- D) `state:modified & tag:nightly`

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | A **space** between selectors = **union**. This runs models that are modified OR tagged `nightly` (whichever set is larger). |
> | **B) ✅ Correct** | A **comma** between selectors = **intersection**. `state:modified,tag:nightly` selects only the nodes that satisfy BOTH conditions simultaneously. This is the correct syntax for "modified AND tagged". |
> | **C) ❌ Incorrect** | The `+` attached to a selector adds graph depth (parents/children), not set intersection. This is invalid for combining two different selectors. |
> | **D) ❌ Incorrect** | `&` is not valid dbt set operator syntax. |
>
> > 💡 **Key rule**: **Space = union** (either/or). **Comma = intersection** (both/and). This is one of the most commonly confused distinctions in dbt node selection.

### Q3. ⭐
> **Subdomain 10.3 — `state:modified` cannot detect `--vars` changes**

A team uses CI slim builds with `dbt run --select state:modified+ --state ./prod-manifest`. They discover that changing a variable value passed via `--vars` never triggers the dependent models to rebuild — even models that use `{{ var('some_var') }}` in their SQL. Why?

- A) `state:modified` compares compiled SQL, so any variable change would be detected.
- B) `state:modified` compares node configurations in the manifest, and `--vars` runtime values are not stored in the manifest.
- C) `--vars` changes are detected only when using `state:modified.configs`, not `state:modified`.
- D) The `--state` flag must be combined with `--vars` for variable changes to be tracked.

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `state:modified` compares the **manifest at parse time**, not compiled SQL. Compiled SQL is only generated by `dbt compile` or during `dbt run`. |
> | **B) ✅ Correct** | `state:modified` checks `manifest.json` contents. `--vars` values are passed at **runtime**, after the manifest is written, so they are **never captured** in the manifest. dbt has no mechanism to detect that a variable value changed between runs. This is a documented limitation. |
> | **C) ❌ Incorrect** | `state:modified.configs` checks model-level config blocks (e.g., `materialized`, `tags`), not runtime variable values either. |
> | **D) ❌ Incorrect** | Combining `--vars` with `--state` has no effect on change detection for variable values. |
>
> > 💡 **Key rule**: `--vars` changes are **invisible to `state:modified`**. If you need variable-driven model changes detected in CI, consider encoding the variable into a config or tag, or explicitly naming the affected models.

### Q4. ⭐
> **Subdomain 10.4 — Manifest overwrite problem**

A CI pipeline runs `dbt run --select state:modified+ --state ./target --target-path ./target`. The team notices the slim CI always builds every model, not just modified ones. What is the root cause?

- A) `--state` and `--target-path` cannot be used together; they are mutually exclusive flags.
- B) When `--state` and `--target-path` point to the same directory, dbt overwrites `manifest.json` during the parse phase before it can be used for comparison.
- C) The `state:modified` selector requires a separate `--profiles-dir` to work correctly.
- D) `--target-path` must point to an absolute path, not a relative path, for state comparison to work.

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | These flags are not mutually exclusive — but pointing them at the same directory is the bug. |
> | **B) ✅ Correct** | At the start of every dbt invocation, dbt parses the project and **writes a new `manifest.json`** to `--target-path`. If `--state` points to the same directory, the **fresh manifest overwrites the comparison baseline** before state comparison can happen. Result: no nodes appear modified, so either everything or nothing is selected (depending on the command). Always keep `--state` pointing to a **separate directory** containing the production manifest. |
> | **C) ❌ Incorrect** | `--profiles-dir` is unrelated to state comparison. |
> | **D) ❌ Incorrect** | Relative vs absolute path is not the issue here. |
>
> > 💡 **Key rule**: **Never point `--state` and `--target-path` at the same directory.** dbt overwrites `manifest.json` on parse, destroying the comparison baseline. Use a separate path like `--state ./prod-manifest`.

### Q5. ⭐
> **Subdomain 10.5 — `--defer-state` for split comparison and deferral**

A team wants their CI slim build to compare modified nodes against the **production** manifest, but defer missing relations to the **staging** environment (which has fresher data). Which flag combination achieves this?

- A) Use `--state ./prod-manifest --defer` — dbt automatically defers to the staging environment when relations are missing.
- B) Use `--state ./prod-manifest --defer --defer-state ./staging-manifest` — `--state` drives comparison; `--defer-state` drives deferral resolution.
- C) Use `--defer-state ./staging-manifest` alone — this flag handles both comparison and deferral.
- D) This is not possible in dbt; `--state` and deferral must use the same manifest.

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `--defer` alone defers to whatever manifest `--state` points to — there is no automatic environment detection. |
> | **B) ✅ Correct** | `--defer-state` is a separate flag that lets you specify a **different manifest** for deferral resolution than the one used for `state:modified` comparison. `--state` answers "what changed?" and `--defer-state` answers "where do I find existing relations to defer to?" This is ideal when production is the authoritative baseline but staging has more recent data. |

### Q6. ⭐
> **Subdomain 10.6 — `--indirect-selection` modes**

A test selects only `model_a` using `dbt test --select model_a`. The project has a `relationships` test between `model_a` and `model_b`. Which `--indirect-selection` mode would **exclude** that relationships test?

- A) `eager` (default)
- B) `buildable`
- C) `cautious`
- D) `empty`

> [!success]- Answer & Explanations
> **✅ Correct: C or D** — See explanation. This question asks which modes **exclude** relationship tests.
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `eager` (default) = include a test if **any** of its parents are selected. `model_a` is selected, so the relationship test IS included. |
> | **B) ❌ Incorrect** | `buildable` = include a test if it can be executed given the selected models and their ancestors. The relationship test would still run if `model_b` is upstream or available. |
> | **C) ✅ Correct** | `cautious` = include a test only if **all** its parents are selected. Since `model_b` is NOT in the selection, the `relationships` test (which references both `model_a` and `model_b`) is excluded. |
> | **D) ✅ Correct** | `empty` = **no indirect tests** are selected at all — only tests that directly belong to a selected node. All multi-node tests like `relationships` are excluded. |
>
> > 💡 **Key rule**: `eager` = any parent selected → run test. `cautious` = all parents selected → run test. `empty` = no indirect tests ever. Use `cautious` or `empty` in CI to avoid cross-environment false failures from relationship tests.

### Q7. ⭐
> **Subdomain 10.7 — `dbt build` unit test execution order**

A data engineer adds a unit test to `model_x`. When `dbt build` runs, in what order does the unit test execute relative to the model materialization?

- A) Unit tests run after model materialization, then data tests run last.
- B) Unit tests run before model materialization; data tests run after materialization.
- C) Unit tests and data tests both run after model materialization.
- D) Unit tests run at the start of the entire `dbt build` job before any models are materialized.

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | Unit tests do NOT run after materialization. Their entire purpose is to validate model logic before the model is written to the warehouse. |
> | **B) ✅ Correct** | `dbt build` execution order per node: **unit tests → model materialization → data tests**. Unit tests run on mock input data (no warehouse read) before the model is materialized. If a unit test fails, the model is never materialized. Data (schema) tests run after the model exists in the warehouse. |
> | **C) ❌ Incorrect** | Unit tests specifically run before materialization — that is their defining characteristic. |
> | **D) ❌ Incorrect** | Unit tests respect the DAG order; they run for each node in dependency order, not all at once before the DAG starts. |
>
> > 💡 **Key rule**: `dbt build` per-node sequence: **unit test → materialize → data test**. Unit test failure = model never runs. Data test failure = downstream nodes are skipped (not errored).

### Q8. ⭐
> **Subdomain 10.8 — `dbt build` upstream test failure behavior**

A `dbt build` run executes `model_a` successfully, then `model_a`'s data tests fail. `model_b` depends on `model_a`. What is the outcome for `model_b`?

- A) `model_b` runs anyway — test failures in upstream models do not block downstream builds.
- B) `model_b` errors — the test failure propagates as an error to all downstream nodes.
- C) `model_b` is skipped — test failures in upstream models cause downstream nodes to skip, not error.
- D) `model_b` runs but its own tests are skipped as a precaution.

> [!success]- Answer & Explanations
> **✅ Correct: C**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `dbt build` is specifically designed to halt downstream work when upstream tests fail. |
> | **B) ❌ Incorrect** | Downstream nodes receive `skipped` status, not `error`. The error is on the upstream test itself. |
> | **C) ✅ Correct** | When an upstream data test fails in `dbt build`, all downstream nodes are **skipped** (status = `skipped`). ### Q9. ⭐
> **Subdomain 10.9 — `dbt retry` and infrastructure failures**

A dbt Cloud job fails due to a warehouse connectivity error before any nodes begin executing. The run results file shows zero nodes attempted. A developer runs `dbt retry`. What happens?

- A) `dbt retry` re-runs all models in the project since no successful runs exist.
- B) `dbt retry` is a no-op — if no nodes executed before the failure, there are no failed nodes to retry.
- C) `dbt retry` falls back to running the full model selection defined in the job.
- D) `dbt retry` raises an error and requires `--full-refresh` to proceed.

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `dbt retry` reads `run_results.json` to find failed/errored nodes — it does not infer a full run when results are empty. |
> | **B) ✅ Correct** | `dbt retry` reads the `run_results.json` from the previous run and retries only nodes that `errored` or `failed`. If the failure was an infrastructure error before any nodes started (empty results), there is nothing to retry — `dbt retry` is effectively a **no-op**. The developer must re-run the job manually or fix the infrastructure issue first. |
> | **C) ❌ Incorrect** | `dbt retry` does not fall back to the job's original model selection. It is strictly `run_results.json`-driven. |
> | **D) ❌ Incorrect** | `dbt retry` does not raise errors or require `--full-refresh` in this scenario. |
>
> > 💡 **Key rule**: `dbt retry` = replay only `errored`/`failed` nodes from `run_results.json`. Infrastructure failure with zero executed nodes = **no-op retry**. Must re-run the job from scratch.

### Q10. ⭐
> **Subdomain 10.10 — `dbt clone` zero-copy behavior by platform**

A team runs `dbt clone` to create a developer-scoped copy of production models for a hotfix branch. Their warehouse is Postgres. What does `dbt clone` create for each cloned model?

- A) A zero-copy clone using Postgres's native table clone syntax.
- B) A full materialized copy of each table, duplicating all data.
- C) A view pointing to the production relation, acting as a lightweight proxy.
- D) A schema-only empty table with no data.

> [!success]- Answer & Explanations
> **✅ Correct: C**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | Postgres does not support zero-copy cloning (metadata pointer swaps). That capability is limited to Snowflake, Databricks, and BigQuery. |
> | **B) ❌ Incorrect** | `dbt clone` explicitly avoids full data copies — full table copies defeat the purpose of fast developer environment setup. |
> | **C) ✅ Correct** | On platforms without zero-copy clone support (Postgres, Redshift), `dbt clone` creates a **pointer view** — a `CREATE VIEW AS SELECT * FROM <production_relation>`. It's a lightweight proxy, not a copy. Reads go through to the underlying production table. |
> | **D) ❌ Incorrect** | `dbt clone` creates a usable relation (view or clone), not an empty schema. |
>
> > 💡 **Key rule**: `dbt clone` zero-copy support: **Snowflake** (CLONE), **Databricks** (shallow clone), **BigQuery** (dataset copy). **Postgres/Redshift** = pointer views. All behavior is automatic based on the adapter.

### Q18. ⭐
> **Subdomain 10.18 — `result:error` vs `result:fail` selectors**

After a failed `dbt build`, a developer wants to retry only the nodes that **errored** (e.g., models that failed to compile or run) while explicitly excluding tests that failed due to data quality issues. Which selector is correct?

- A) `result:fail`
- B) `result:error`
- C) `result:error result:fail`
- D) `state:modified.body`

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `result:fail` selects nodes with status `fail` — this is the status assigned to **tests** that fail (data quality assertion failures). It does not select errored models. |
> | **B) ✅ Correct** | `result:error` selects nodes with status `error` — this is the status assigned to **models, seeds, and snapshots** that encounter execution errors (bad SQL, permission denied, compile errors). Tests that error (not fail) are also included. Use `result:error` to retry failed model execution without re-running passing tests or skipping data-failing tests. |
> | **C) ❌ Incorrect** | The space between these selectors = union (either errored OR failed). This would re-run both failing models and failing tests — not the desired behavior if you want to exclude data quality test failures. |
> | **D) ❌ Incorrect** | `state:modified.body` is a state comparison selector for detecting SQL body changes, not for retrying failed nodes. |
>
> > 💡 **Key rule**: `result:error` = execution failures (models, commands). `result:fail` = assertion failures (tests). These are distinct statuses. `dbt retry` internally uses `result:error+result:fail` to catch both.

### Q19. ⭐
> **Subdomain 10.19 — `dbt compile --inline` for ad-hoc SQL**

A developer wants to compile a Jinja SQL snippet that uses `{{ ref('orders') }}` without creating a model file. Which command accomplishes this?

- A) `dbt run --inline "SELECT * FROM {{ ref('orders') }}"`
- B) `dbt compile --inline "SELECT * FROM {{ ref('orders') }}"`
- C) `dbt parse --inline "SELECT * FROM {{ ref('orders') }}"`
- D) `dbt compile --ad-hoc "SELECT * FROM {{ ref('orders') }}"`

> [!success]- Answer & Explanations
> **✅ Correct: B**
>
> | | |
> |---|---|
> | **A) ❌ Incorrect** | `dbt run` does not support `--inline`. It executes model files, not inline SQL. |
> | **B) ✅ Correct** | `dbt compile --inline "<sql>"` compiles an ad-hoc Jinja SQL string without requiring a model file. It resolves `{{ ref() }}`, `{{ source() }}`, macros, and variables against the current project and target, then prints the compiled SQL. Useful for debugging Jinja expressions or quickly checking what a snippet compiles to. Note: requires a **warehouse connection** (like all `dbt compile` invocations). |
> | **C) ❌ Incorrect** | `dbt parse` does not support `--inline`. It parses project files, not inline SQL. |
> | **D) ❌ Incorrect** | `--ad-hoc` is not a valid dbt flag. |
>
> > 💡 **Key rule**: `dbt compile --inline "<jinja-sql>"` = ad-hoc compilation of a SQL snippet. No model file needed, but warehouse connection required. Great for Jinja debugging.

### Q20. ⭐
> **Subdomain 10.20 — `--favor-state` flag behavior**

A developer runs `dbt run --select orders+ --defer --state ./prod-manifest`. For nodes that exist in both the dev target (partially built from yesterday) and the production manifest, which relation does dbt use by default? **Select TWO correct answers.**

- A) By default (no `--favor-state`), dbt prefers the **dev target** relation if it exists there.
- B) By default (no `--favor-state`), dbt prefers the **production manifest** relation always.
- C) Adding `--favor-state` causes dbt to prefer the **state manifest** (production) relation over the dev target.
- D) Adding `--favor-state` causes dbt to prefer the **dev target** relation over the state manifest.

> [!success]- Answer & Explanations
> **✅ Correct: A, C**
>
> | | |
> |---|---|
> | **A) ✅ Correct** | The **default `--defer` behavior** prefers the developer's own target schema. If a relation exists in the dev target (even if outdated), dbt uses it — deferring to production only for relations that do NOT exist in dev at all. |
> | **B) ❌ Incorrect** | Without `--favor-state`, production is the fallback, not the preference. Dev target takes priority when a relation exists there. |
> | **C) ✅ Correct** | `--favor-state` **flips the priority**: dbt now prefers the state manifest (production) relation over whatever is in the dev target. This ensures developers always work against production-fresh data even when stale dev relations exist. |
> | **D) ❌ Incorrect** | This describes the default behavior (no `--favor-state`), not what `--favor-state` adds. |
>
> > 💡 **Key rule**: Default `--defer` = dev target first → prod state as fallback. `--favor-state` = prod state first → dev target as fallback. Use `--favor-state` in CI or when dev relations may be stale.

### Q21. ⭐
> **Subdomain 10.21 — `source:` vs `source_status:` selector methods**

A platform team wants to build only the models downstream of sources whose raw data has actually arrived since the last run. They author a job with the step:

```bash
dbt build --select source:fresher+
```

The job runs successfully but builds **zero models**, even though new data has clearly landed in some sources. What is the issue, and what is the correct command? **Select TWO correct answers.**

- A) `source:fresher+` is interpreted as a **name lookup** for a source literally named `fresher`. Unless one exists, the selector matches nothing and the run is a silent no-op.
- B) The correct selector method for "sources with new data since the last freshness check" is `source_status:fresher+`, which compares the current `sources.json` against a prior one provided via `--state`.
- C) `source:fresher+` is the correct selector but requires the `--full-refresh` flag to register new freshness state.
- D) `source_status:` accepts multiple values such as `fresher`, `stale`, and `error` — the team should use `source_status:fresher,stale+` to capture all changes.
- E) The job will work as written if the team upgrades to the Fusion engine, which auto-resolves `source:fresher+` as a freshness-state selector.

> [!success]- Answer & Explanations
> **✅ Correct: A, B**
>
> | | |
> |---|---|
> | **A) ✅ Correct** | `source:` is the **name-based** selector method — it expects a source's declared name (e.g., `source:snowplow+`). `source:fresher+` is interpreted as "find a source literally **named** `fresher` plus its descendants." Since virtually no project defines a source by that name, the selector resolves to **zero nodes** and the run silently does nothing. This is one of the most common dbt selector traps. |
> | **B) ✅ Correct** | The correct selector is **`source_status:fresher+`** — a state-aware selector that compares the current `sources.json` (from a fresh `dbt source freshness` run) against a prior one supplied via `--state path/to/previous/`. Sources whose `max_loaded_at` is newer in the current run are tagged `fresher` and selected, along with their downstream models. The full correct command is: `dbt build --select source_status:fresher+ --state path/to/previous/`. Without `--state`, this also resolves to zero nodes. |
> | **C) ❌ Incorrect** | `--full-refresh` controls incremental rebuild behavior — it has no relationship to freshness state detection. The underlying selector method is still wrong. |
> | **D) ❌ Incorrect** | `source_status:` accepts **only one value: `fresher`**. There is no `stale` or `error` variant. (Errors and staleness are surfaced by `dbt source freshness` exit codes, not by this selector.) |
> | **E) ❌ Incorrect** | The Fusion engine does not change selector method semantics. `source:` remains a name lookup regardless of engine. |
>
> > 💡 **Key rule**: `source:<name>+` = **name lookup** (no `--state` needed). `source_status:fresher+` = **state-aware freshness selector** (requires `--state` with prior `sources.json`; `fresher` is the only valid value). Mistyping `source_status` as `source` is a silent no-op, not an error.
